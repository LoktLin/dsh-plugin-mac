# 发布文档内检（README / CHANGELOG / 发布说明）

> 用途：发布前对面向使用者的文档做一次「无意义说明」内检——**默认读者是第一次拿到这个版本的人，或要调用这些工具的 AI Agent**。
> 触发：要发 npm 版本 / 写 release notes / 改 README 描述 / 交接插件给他人。

---

## 一、默认读者

第一次拿到这个版本的使用者，或要调用这些工具的 AI Agent。
**不是维护者，不在你本机，不关心仓库内部怎么管理、文档从哪挪到哪、谁帮了谁。**

写作与审查时用这一条反问：这句话对"刚装上包、想把它用起来"的人有动作价值吗？

---

## 二、保留判据（一句话满足至少一条才留）

1. 影响**安装、升级、调用、配置、排障**；
2. 说明**兼容性、平台、版本、许可证、安全、破坏性变更**；
3. 给出**可执行命令、参数、默认值、返回值、错误语义**；
4. 是读者 / AI Agent 完成当前任务**必须知道**的边界、禁止事项、路径来源；
5. 能帮读者判断**"我该用哪个工具 / 下一步做什么"**。

否则默认删除。

---

## 三、默认删除（重点）

- 迁移史、日期、从哪个目录挪到哪、为什么不在包里、谁帮的是谁；
- 内部路径、工作区文档、`_ref/`、只读克隆、上游源码索引（除非读者必须去那里才能用）；
- "这讲的是……帮的是……不是……"这类自我解释；
- 括号套括号、破折号补充来源、许可结论、维护者备注；
- "不在本包，故不作链接"、"2026-10-01 从本仓库 docs/ 挪过去"这类对读者无动作的信息；
- 重复的"详见 docs/xxx"、重复免责声明；
- 空泛评价："更可靠""更好用""不会过时""优化了体验"；
- 作者心路、决策过程、历史原因、内部考古。

**本项目高频违规形态**（写插件文档时尤其容易犯，因为工程过程本身很精彩）：

| 违规形态 | 例子 | 处置 |
|---|---|---|
| 工程史叙事 | "起因是用户的两个问题……审计结果……" | 删（要留就移开发文档） |
| 自检/项数统计 | "自检 663 → 676 项"、变异测试红了几条 | 删——对使用者不可观测 |
| 自指项数 | "文档绊线 24 项" | 删（写"它守什么"而非项数） |
| 内部路径与审计产物 | `/tmp/lanhu-audit/`、`~/.dsh/lanhu/audit-20260921/` | 删 |
| 复盘与教训 | "复盘结论：能力早就够了，缺的是……" | 删或移 pitfalls |
| 未验证项的内部口径 | "未在全部 1437 张稿回归" | 删；只有**影响使用**的局限才留（如"该场景返回 null"） |
| 发布流程内务 | git 历史清理、tag 前移、SHA 变化 | 删或移 CONTRIBUTING |
| 同期做过又撤掉的东西 | 面板第 4 个 Tab 撤掉的理由 | 删或移开发文档 |

---

## 四、保留并压缩

- 安装命令、版本要求、平台限制、许可证；
- **破坏性变更、迁移步骤、已知坑、安全警告**；
- 工具名、`op`、参数、默认值、返回值、错误语义；
- AI Agent 执行所需的路径来源、禁止写死、只写哪些目录等硬边界；
- **真正可达且读者需要**的链接，写成"用途 + 直达链接"，不写迁移史。

压缩成一句的典型：把"某版做了什么 + 为什么 + 验证方式"三段压成**"你会看到什么变化 + 要不要动手"**一行。

---

## 五、处理方式（每处只选一种）

**删除 / 压缩成一句 / 移到维护者文档 / 改成读者动作。**

- 信息只对维护者有用 → 写"建议移到 CONTRIBUTING 或开发文档"，**不要留在 README / CHANGELOG**；
- 无法判断 → 标 `[待确认]`，**不要编造理由**。

---

## 六、输出格式（固定）

```markdown
## 内检结果
删除 X 处，压缩 Y 处，保留 Z 处，待确认 W 处。

## 修订版
直接给可替换原文的全文。

## 删除/压缩清单
| 原文 | 类型 | 处理 | 理由 |
|---|---|---|---|

## 待确认
最多 3 条。
```

---

## 七、最后自检（逐条过）

- 修订版是否更短、信息密度更高？
- 是否还有"文档在解释自己"的句子？
- 是否还有内部路径、日期、迁移史、嵌套括号？
- 每个链接读者是否真的能到达？不能就删。
- 如果我是第一次用这个包的人或 AI，**只读修订版**，能不能完成安装/调用/排障？

---

## 八、执行提示

- **内检员不改技术事实**：只删/压/搬，不改数值、参数、行为描述；发现事实存疑就进「待确认」，不擅自改。
- 修订版仍然要能被 `README` 的链接检查与项数绊线接受（本技能 `scripts/` 下有自检脚本）；
  改完 CHANGELOG/README 后跑一次 `node test/readme-test.mjs`（插件仓库自带）与技能自测。

---

## 九、机械层脚本（先跑它，再做判断）

```bash
S=~/.dsh/skills/dsh-plugin-mac/scripts/review-release-doc.mjs

node $S <文件.md>                 # 扫并报告（分规则列候选 + 处置建议 + 汇总计数）
node $S <文件.md> --json          # 机器可读（CI 卡口）
node $S <文件.md> --only D1,D4    # 只跑指定规则
node $S <文件.md> --ignore D1     # 跳过指定规则
node $S <文件.md> --include-code  # 连代码块内也扫（默认跳过：样例输出里的日期/路径是技术事实）
node $S <文件.md> --root <目录>   # 校验相对链接存在性时的根目录（默认文档所在目录）
node $S --list-rules              # 列出全部规则与判据
node $S --selftest                # 规则自证：正例必须命中、负例必须不命中
```

**退出码**：`0` 无命中 ｜ `1` 有命中（CI 可据此卡口）｜ `2` 用法错误 / 文件读不到。

| 规则 | 抓什么 | 处置建议 |
|---|---|---|
| D1 | 日期（`2026-10-08`、`2026 年 9 月`、RFC-2822） | 删除 |
| D2 | 迁移史 / 来源交代（挪用、`_ref/`、只读克隆、原是独立技能） | 删除 |
| D3 | 内部路径 / 内部文档引用（`/tmp/…`、`/Users/…`、内部排查记录、审计产物） | 删除 |
| D4 | 自测项数 / 覆盖率统计（`自检 N 项`、变异测试、黄金输出对比） | 删除 |
| D5 | 复盘叙事 / 教训（"起因是…"、"根因是…"、踩坑记） | 移维护者文档 |
| D6 | 作者心路 / 自我解释（"我决定…"、"如实记录"、"目标是让…"） | 删除 |
| D7 | 空泛评价（更好用 / 更可靠 / 不会过时 / 更体面） | 删除 |
| D8 | 嵌套括号 / 破折号塞来源（"—— 见 §3"） | 压缩成一句 |
| D9 | 内部验证史 / 未验证项（"未跑满…"、"验证方式…"、夹具、断言 N 条） | 移维护者文档 |
| D10 | 维护者内务（git 历史 / tag / SHA / 发布清单） | 移维护者文档 |
| D11 | 重复的"详见 docs/xxx"（同一文档被指向 >2 次） | 压缩成一句 |
| D12 | 相对链接可能不可达（文件不存在） | 删除或改绝对地址 |

**它能做什么、不能做什么**：机械项（日期/路径/统计/叙事/链接可达性）**可靠**；「压缩成一句 vs 移到维护者文档」的取舍、以及"这句话有没有动作价值"的最终判断**仍要人过一遍**。所以脚本**没有 `--fix`，从不改文件**。

### 规则维护纪律（两条，别省）

1. **每条规则必须有自证**：`--selftest` 里带**正例**（必须命中）与**负例**（必须 0 命中）。没有正例的规则就是"永远报警的噪音"；没有负例的规则就会训练人忽略这个脚本。
2. **假警报要当场调规则，不要容忍**：本项目实测两例——`~/.dsh/**` 在 README 里是**必需的**安装/Cookie 路径（不是内部路径），`—— 详见 [链接]` 是**正常指路**（不是"破折号塞来源"）。两条都收紧了规则并写进夹具负例（README 误报 13 → 6 处，而目标文档的真阳性命中 101 → 100 处基本不变）。
3. **`\w` 不匹配中文**：文件名/路径正则一律用 `[^\s)`（）]+` 这类宽松字符类，否则 `docs/CLI与开发.md` 这种中文文件名会**静默漏报**（本项目真踩过，自证夹具已锁）。
